## Architecture

This is a **CakePHP 5.1** application (PHP 8.1+) running under XAMPP. It acts as a JSON API backend consumed by a React frontend at `http://localhost:3000`. The backend is deployed via Docker to **Railway** (prod API `https://api.career-pass.org`); the frontend deploys to **Cloudflare Pages** (prod site `https://career-pass.org`, `www.` 301s to apex). Frontend and API are **same-site** in prod (both under `career-pass.org`). See **Deployment** for domains/DNS.

**The question bank can't be downloaded (H2).** Questions are reachable only as practice sets and one-at-a-time answer checks: there is deliberately no `GET /api/questions` list or `GET /api/questions/:id` view (both 404 — they once returned the whole bank with its answer key), and `GET /api/topics/:id` carries no questions. `practice` returns randomized questions with shuffled choices; accepts `?topic_id=` and `?limit=` (1–50, default 20). It sends **no `is_correct` and no `explanation`** (both are `$_hidden` on the `Choice`/`Question` entities) and records the served question IDs in the session (`Practice.served`, the most recent 200). **`POST /api/questions/:id/answer`** `{ choice_id }` checks one answer on the server: AJAX header required; the served check comes **before** the existence check, so a question this session wasn't served — including an ID that doesn't exist — is **403** `{ reason: 'not_served' }` and IDs can't be probed; a served question deleted since is 404; a choice that isn't one of the question's is 422. It returns `{ question_id, correct, correct_choice_id, explanation }`, writes nothing, and allows re-answering. It's the seam for future answer analytics or a graded mock exam. Without `resources('Questions')`, any other `/api/questions…` URL falls through to the default fallback routes (ACTION_PLAN L13) and 404s.

`Api\TopicsController` and `Api\QuestionsController` extend **`App\Controller\Api\AppController`** (a real base class, distinct from the empty dead `src/Controller/ApiController.php`). Its `beforeFilter` gates every request (H1): the **write actions `add`/`edit`/`delete` are disabled** (403 — content comes via `bin/cake import_questions`, no admin UI); **reads need a usable session** — the same `activeUserId()` single-device check as every other signed-in endpoint (see Authentication → Single-device sessions), else **401** `{ reason: 'signed_out' | 'signed_in_elsewhere' }`; and the checked user (never the session's copy) must **hold an active `paid` pass**, else **403** `{ reason: 'no_active_pass' }` (the bank is paid content). Before H1 this gate read `Auth.User` without comparing `session_token`, so a device signed out by a login elsewhere kept reading content. The answer check above sits behind the same gate. The frontend consumer is `src/pages/Practice.js` (`/practice`, topic picker → question → submit → reveal + explanation → score + review; each submit calls `submitAnswer()` in `src/api.js`, and the reveal, score and review use the server's verdicts), routed in `Dashboard.js` and linked from `Review.js`. `Practice.js`, `TopicReview.js` and `Review.js` treat a 403 `no_active_pass` as "no pass" (show the pass card/banner, keep the session) even when the stored user's purchases still list one.

`TopicsController::view()` (`GET /api/topics/:id`) returns the topic and its **`TopicReview`** only — no questions since H2 (a topic's study/explainer write-up — see Data Model), so a topic's page always gets its content in one call. Frontend: `src/pages/TopicReview.js` (`/review/:reviewer/topics/:topicId`, routed in `Dashboard.js`) — the "how this topic is easy to answer" read that `Review.js`'s topic cards link to; it's deliberately *not* another quiz (that's still `/practice`, linked from a CTA at the bottom of the page). Topic content is plain paragraphs (blank-line-separated), not markdown — no markdown renderer is in the frontend's `package.json`.

Controllers in the `Api\` namespace live under `src/Controller/Api/`. Auth/account routes (`login`, `register`, `logout`, `session`, `google-login`, `account/setup`, `account/email`, `account`) are handled by `UsersController` in the root namespace and connected explicitly (not via `resources()`). `updateAccount` (`POST /api/account`) patches profile fields only (name/username) for the logged-in user — never the password, and never the email (that's `changeEmail`, H3).

**Dead code — do not edit by mistake:** `src/Controller/Api/LoginController.php` (a legacy `sessionCheck`/`logout`/`options` stub using the removed `RequestHandler` component) and `src/Controller/ApiController.php` (empty) are unrouted leftovers. The live auth logic is entirely in `UsersController`.

### CORS & Middleware

CORS is handled by `CorsMiddleware` (`src/Middleware/CorsMiddleware.php`), added **first** in the `Application.php` middleware queue. It reads **one** allowed origin from the `FRONTEND_URL` env var (dev default `http://localhost:3000`, prod `https://career-pass.org`) — echoed verbatim into `Access-Control-Allow-Origin`, so it must be scheme+host with **no trailing slash** and no path, and there is **no multi-origin support** (a second frontend domain would need a code change). Also sets `Access-Control-Allow-Credentials: true`. Preflight `OPTIONS` requests are short-circuited inside the middleware before hitting routing.

CORS for every action, auth included, comes solely from `CorsMiddleware` — do not add per-action `Access-Control-*` headers (`login()` used to force `Access-Control-Allow-Origin: *`, which conflicts with credentialed CORS; that was removed).

**No CSRF middleware is registered at all** — it was removed entirely (not merely skipped for `/api/`) to allow the cross-origin SPA to POST. The full queue is: `CorsMiddleware` → `ErrorHandlerMiddleware` → `AssetMiddleware` → `RoutingMiddleware` → `BodyParserMiddleware`.

**CSRF is instead enforced per-action** by `requireAjaxHeader()` — defined once in `App\Controller\SessionAuthTrait`, which the root `AppController` uses, so every controller has it — called at the top of every state-changing auth/account/checkout action (`login`, `register`, `logout`, `googleLogin`, `setupAccount`, `updateAccount`, `forgotPassword`, `resetPassword`, `changePassword`). It 403s any request without `X-Requested-With: XMLHttpRequest`. The reasoning: a plain HTML `<form>` POST (the classic CSRF vector) can't set custom headers, and a cross-origin `fetch`/XHR that does set one triggers a CORS preflight that `CorsMiddleware` only allows for `FRONTEND_URL` — so the header requirement reuses the existing CORS policy as an effective CSRF check. Any new auth action must call this gate; any new frontend caller must go through the `api` axios instance in `webroot/react-frontend/src/api.js` (which sets that header + `withCredentials`), not a bare `axios`/`fetch`.

Session cookies are configured (`config/app.php` → `Session.ini`) as `SameSite=None; Secure; HttpOnly` — required for the cross-origin SPA to send them at all, which is also *why* the header gate above is needed.

### Authentication

Authentication is manual — no CakePHP Auth or Authentication plugin is used. All actions write/read the session key `Auth.User`.

- **`login()`** — `password_verify()` against the stored `user_pass` hash, then `session()->write('Auth.User', $user)`. On a successful verify it also runs `password_needs_rehash()` and re-stores the hash if PHP's `PASSWORD_DEFAULT` has since moved on (persisted by the `startSession()` save). If the matched user has `user_pass === null` (a Google-only account), it returns `200` with `{ success: false, needsGoogleSetup: true, account: {...} }` so the SPA can prompt "continue with Google to finish setup" instead of showing a generic error. A correct password on an account whose email isn't verified yet doesn't sign in: it emails a fresh code (cooldown permitting) and returns `needsVerification` (see **Email verification** below). **Brute-force throttle:** `loginThrottle()` runs before the password check — ≥ `LOGIN_MAX_FAILURES` (10) failed attempts for the same identifier (lowercased username/email) within `LOGIN_FAILURE_WINDOW_MINUTES` (15) returns `429` without checking the password. Each wrong password / unknown account writes a `login_attempts` row (`recordLoginFailure()`, which also prunes day-old rows); a correct password clears that identifier's rows (`clearLoginFailures()`). This is per-identifier only — no per-IP limit, since Railway's proxy makes `REMOTE_ADDR` unreliable without trusted-proxy config.
- **`googleLogin()`** — verifies a Google ID token (`credential` in the POST body) against the `GOOGLE_CLIENT_ID` env var through **`App\Auth\GoogleTokenVerifierInterface`** (real implementation `GoogleTokenVerifier`, wrapping `google/apiclient`'s `verifyIdToken()`), which is registered in `Application::services()` and injected into the action, so tests swap it with `mockService()`. A credential that isn't a token at all → **400** "Invalid Google credential"; a well-formed but invalid one (bad signature, expired, wrong audience, or signed by a key Google doesn't publish — php-jwt's `OutOfBoundsException`) → **401** "Invalid Google token"; only failing to reach Google's key server is a 500. The token must carry an email with `email_verified === true`, else **403**. User lookup order: by `google_id`, then by `email`, then creates a new user (already verified) with a de-duplicated `user_name` derived from the email local-part. An email match on a **verified** account that isn't linked to this Google account is **linked only after an emailed code** (B3-L, `linkVerifiedAccount()`): Google's `email_verified` says who controlled the address when Google checked it, not now. The first request gets `200 { success: false, needsLinkCode: true, email, message }` and a `link_google` code (same cooldown/cap as verification codes). The second request **sends the same Google credential again** with `code`: the token is verified again and nothing is kept in the session. The right code attaches `google_id`, signs in and emails "Google sign-in was added to your CareerPass account"; a wrong, expired or used code → **400**. If the matched account is already linked to a **different** Google account → **409** "This account is already connected to a different Google account…", with no code, no change, no session and a `[warning]` log line. Relinking is never a side effect of signing in (the old code silently overwrote `google_id`). An email match on an **unverified** account is a **takeover** (`takeOverUnverifiedAccount()`, one transaction): Google proves the inbox, so the unproven password is cleared, `session_token` rotated, every `auth_codes` and `login_events` row deleted, `google_id` attached, the email marked verified, and `fname`/`lname` replaced by Google's when given (`user_name` is kept); it returns `isNewUser: true` so the owner lands on account setup. On success writes `Auth.User` and returns `isNewUser` so the frontend can route brand-new sign-ups to account setup.
- **`setupAccount()`** — for a logged-in Google-only account (`user_pass` is null): sets a password for the first time (and optionally touches up `fname`/`lname`/`user_name`). 409s if a password already exists. **Two-step**: the first call (no `code`) emails a `set_password` code and returns `{ needsCode: true }`; the second call must include it. Rewrites `Auth.User` on success.
- **`changePassword()`** — `POST /api/password/change`, logged-in + AJAX-gated. Needs `current_password` + `new_password`, which must be different. Rotates `session_token` (signs out other devices) but updates `Auth.token` on the current session so this device stays in, and emails a "password was changed" notice.
- **`updateAccount()`** — `POST /api/account`, logged-in + AJAX-header gated. Patches `fname`/`lname`/`user_name` only (never `user_pass`), re-writes `Auth.User`. Backs the Settings page profile form. A request whose `email` differs from the current address (ignoring case) gets **422** "Use 'Change email' in Settings to update your email address." and nothing is saved; sending the current email back unchanged is fine (old tabs still post it).
- **`changeEmail()`** (H3) — `POST /api/account/email`, logged-in + AJAX-header gated. Every request carries `new_email`; nothing is stored between steps. **Re-authenticate**: `{new_email, current_password}`, or for an account without a password `{new_email}` (an `email_change_reauth` code to the **current** address, `needsCurrentCode`, the address masked) then `{new_email, current_code}`. Either way a `change_email` code then goes to the **new** address (`needsCode`). **Confirm** with `{new_email, code}`: a `change_email` code is only ever issued after re-authentication, so it proves both. Both codes are **bound to the new address** — the stored hash is of `code | sha256(normalized new email)`, digested so it fits bcrypt's 72-byte input — so a code never works for another address. The current-address code is checked but not used up at step 2 (so "Send a new code" can repeat that step) and is deleted when the change completes. On confirmation, in one transaction: `email` set as typed, `email_verified_at` = now, `session_token` rotated (other devices signed out, this one kept via `Auth.token`), and every outstanding actionable code deleted (rows with a non-empty `code_hash`; the `<purpose>_sent` limit rows stay). Then a notice to the old address (new address masked, e.g. `a***@gmail.com`, plus support@career-pass.org) and a confirmation to the new one. Errors: **422** for a malformed address, one over 100 characters, the current address, or one already registered (all ignoring case; a duplicate-key race is the same 422); **400** for a wrong password or a wrong/expired/used/mismatched code. Codes use the same 60 s cooldown and 10/day cap as verification, per purpose. No throttle on wrong current passwords yet (H4). Frontend: `ChangeEmailPanel` in `Settings.js` (two steps with a password, three without); the profile form shows the email read-only.
- **`session()`** — returns `{ loggedIn, user }` and sends `Cache-Control: no-store` / `Pragma: no-cache` so the SPA never gets a stale login state.
- **`logout()`** — `session()->delete('Auth.User')` + `session()->renew()` (deliberately *not* `destroy()`, which caused issues in production).

The serialized `user` object **omits `user_pass` and `session_token`** (`$_hidden` on the `User` entity — `user_pass` used to leak the bcrypt hash into every response and into `localStorage`) and adds a virtual **`password_set`** boolean the Settings/AccountSetup UI uses to show account-completion state. **Mass assignment:** `User::$_accessible` allows only `fname`/`lname`/`email`/`user_name`; `user_pass`, `google_id`, `session_token` and `email_verified_at` are always assigned explicitly in code (`register` used to accept a `google_id` from the request, which let anyone pre-link an account to their own Google login).

**Email verification (B3-V) — no session until verified.** `users.email_verified_at` (NULL = unverified). `register()` creates the account unverified, emails a `verify_email` code and returns `{ success: false, needsVerification: true, email, message }` with **no session**; **`POST /api/verify-email`** (`email` + `code`) checks the code, sets `email_verified_at` and starts the session. Wrong/expired/used codes, unknown emails and already-verified accounts all get the same 400. **`POST /api/verify-email/resend`** (`email`) always answers the same 200 and sends a new code (replacing the old) only when the account exists, is unverified and is past the limits: a **60 s cooldown** and **10 codes per account per 24 h** (with 5 guesses a code, that caps guessing at 50 a day). The sending and both limits live in `sendLimitedCode($user, $purpose, $intro)`, shared with Google linking (B3-L, purpose `link_google`). The limits are counted **per purpose** in code-less `<purpose>_sent` rows in `auth_codes` (`verify_email_sent`, `link_google_sent`), so the two kinds of code don't share a budget — *not* `login_attempts`, whose identifiers come from unauthenticated input and could be used to exhaust someone else's cap. `resetPassword()` also marks the address verified (the reset code proves it), and a Google login proves it (see `googleLogin()`). As a backstop, `startSession()` throws `LogicException` for an unverified account, so no path can sign one in. Frontend: `LoginPage.js` swaps to a "Check your email" step (code field, "Send a new code", "Use a different account") on `needsVerification` from register or login, and to a "Confirm it's you" step (code field, "Verify & connect Google", "Send a new code" — which re-sends the Google credential without a code — and "Cancel") on `needsLinkCode` from either Google button. Verification stops mistyped and unowned addresses, not disposable ones; an email change re-authenticates and verifies the new address first (`changeEmail()`, H3), and abandoned unverified accounts aren't cleaned up (L10).

**Password rules.** Every path that sets a password (`register`, `setupAccount`, `resetPassword`, `changePassword`) runs `UsersController::passwordError()` — min 8, max 72 bytes (bcrypt's silent-truncation limit) — and hashes with `password_hash(PASSWORD_DEFAULT)` (bcrypt). Before this gate existed, `register()` accepted an empty password. The `user_pass` column / validator must stay at **`VARCHAR(255)`** even though bcrypt is 60 chars, so a future `PASSWORD_DEFAULT` (argon2id, ~95 chars) isn't silently truncated. Exception messages from the auth actions are logged server-side via `serverError()` and never returned to the client.

**Email + one-time codes.** `UsersController::sendMail()` picks its transport straight from the environment (not the `Mailer`/`EmailTransport` config, to keep the send path wiring-free): **Brevo's transactional HTTP API** when `BREVO_API_KEY` is set — via `src/Mailer/Transport/BrevoTransport.php`, which POSTs to `https://api.brevo.com/v3/smtp/email` because Railway blocks outbound SMTP — else an SMTP DSN in `EMAIL_TRANSPORT_DEFAULT_URL`, else (neither set) it **`Log::warning`s the message** (`[mail] no transport …`), so code flows stay testable before mail is wired. `EMAIL_FROM` is the sender in all cases. Warning-and-above logs are mirrored to stderr so Railway surfaces them. `config/app.php` also points `EmailTransport.default` at `BrevoTransport` when the key is present, but `sendMail()` does not depend on that. `sendAuthCode()` wraps `sendMail()` for the 6-digit codes; `issueCode()` / `consumeCode()` manage the `auth_codes` rows (6-digit, 10-min TTL, 5 attempts). Both take an optional `$binding` (H3: the normalized new address) that is hashed in with the code, and `consumeCode()` can check without using a code up (`$consume = false`); `sendLimitedCode()` can send to an address other than the account's (`$to`). **Forgot-password** is `POST /api/password/forgot` (always 200, never reveals whether the email exists) → emailed code → `POST /api/password/reset` (`email` + `code` + `password`), which sets the new hash and rotates `session_token` so every existing session is signed out.

**Rapid device-switch guard.** Every completed login writes a `login_events` row (`device_hash` = SHA-256 of the User-Agent). `loginChallenge()` runs on the password path of `login()`: if ≥ `DEVICE_SWITCH_LIMIT` (4) distinct devices logged in within the last 60 s, or a `login_challenge` code is already pending, it emails a code and returns `{ success: false, needsCode: true }` instead of starting a session — the SPA then shows a code field and resubmits `login` with `code`. A correct code clears the guard (deletes that user's `login_events`). `googleLogin()` records events but is never challenged.

**Single-device sessions.** `login()` and `googleLogin()` go through `startSession()`, which rotates `users.session_token` to a fresh random value and stores it in the PHP session as `Auth.token`. `activeUserId()` — the one copy, in **`App\Controller\SessionAuthTrait`** (used by the root `AppController`, so Users, Payments and the `Api\` content controllers all share it; H1 removed the copies Users and Payments each had) — re-reads `session_token` and `email_verified_at` from the DB on every call and returns null, clearing the stale session, when the token no longer matches `Auth.token` (the account has since logged in elsewhere, or had its password changed/reset) or the account is gone or unverified (a B3-V backstop). It records why in `$sessionDenialReason` (`signed_in_elsewhere` / `signed_out`), and **`notLoggedIn()`** returns the standard `401 { message: 'Not logged in', reason }` used by every signed-in Users/Payments action. `session()` then returns `{ loggedIn: false, reason }` with that reason. Sessions predating the column (`session_token` null on both sides) are grandfathered until their next login.

**Frontend sign-out handling (H1).** The SPA (`index.js`) re-checks `/api/session` on tab focus/visibility and every 25 s, so a superseded device signs out promptly. The `api` axios instance (`src/api.js`) also has a response interceptor: a **401 from a content endpoint** (`/api/topics…`, `/api/questions…`) carrying a `reason` clears the stored user and goes to `/`. Every other 401 — a failed Google sign-in, checkout, account, purchases — is left to its caller and never signs the user out. The decision logic lives in `src/sessionErrors.js` (plain functions, unit-tested). Either path stores the reason in `sessionStorage` (`careerpass_signed_out`), and the landing page shows **"You signed in on another device."** or **"Your session is no longer valid. Please sign in again."** (the second for any other lost session — expiry, a deploy, B4). Sign out (`TopNavbar.js`) clears the stored user *before* calling `/api/logout`, so an in-flight session check can't mistake it for an expired session.

**Frontend auth state lives in `localStorage`** (key `skillsprint_user` — unchanged despite the SkillSprint→CareerPass rebrand; renaming it would silently log everyone out), not cookies. This dates from the old `*.pages.dev` ↔ `*.up.railway.app` setup where cross-**site** `SameSite=None` cookies were unreliable; now that both sides are under `career-pass.org` the session cookie *does* round-trip (login was verified working through it this way), but the localStorage gate is still the primary and `/api/session` is the confirmation. `index.js` gates on the localStorage entry first, then confirms against `/api/session` with `withCredentials: true`, and re-polls every 25s while the tab is visible plus on focus/`visibilitychange`. The React route `/account-setup` (`src/pages/AccountSetup.js`) is reachable regardless of login state and self-redirects to `/` when there's no stored user.

### Payments

Access passes (7 / 30 / 90 days, per **reviewer** — `civil-service` today) are bought through **Xendit's Invoice API** (`src/Payment/Xendit.php`, a thin `Cake\Http\Client` wrapper, Brevo-style). `PaymentsController` (root namespace, manual auth like `UsersController`, through the shared `SessionAuthTrait` helpers `requireAjaxHeader()` / `activeUserId()` / `notLoggedIn()`):

- **`checkout()`** (`POST /api/checkout`, logged-in + AJAX gate) — body `{ reviewer, plan_id }`. Amount is taken from `App\Payment\Plans` (server-side price list; the frontend `src/plans.js` is display-only and must be kept in sync), never the client. **Double-invoice guard, checked first:** if a `pending` pass for the same `(user_id, reviewer, plan_id)` was created in the last 5 minutes and has an `invoice_url`, that URL is returned as-is — no new pass, no new Xendit call. This is what actually stops a double-click / extra tab / client-side retry from creating two separate payable invoices (the frontend buttons also self-disable while in flight, but that's not a real guarantee — multiple tabs and retries bypass it entirely). The window is short on purpose so a genuine repeat purchase later isn't blocked; a `paid`/`expired`/`superseded` pass never matches `status = 'pending'`, so it can't false-positive. Otherwise: creates a `pending` `passes` row, calls Xendit for a hosted invoice — passing the pass's `external_id` as `Xendit::createInvoice()`'s idempotency key (sent as `X-IDEMPOTENCY-KEY`; a *second* layer, guarding a narrower case: our own request timing out after Xendit already processed it) — persists both `xendit_invoice_id` and `invoice_url` on the pass, and returns `{ invoice_url }` for the SPA to redirect to.
- **`webhook()`** (`POST /api/xendit/webhook`, **no session** — only `hash_equals` on the `x-callback-token` header vs `XENDIT_WEBHOOK_TOKEN`; 401 otherwise) — the callback body is only a **pointer** (`external_id`): the pass is looked up, then **Xendit's own invoice record is fetched** (`Xendit::getInvoice()`, or `findInvoiceByExternalId()` if checkout never stored the id) and must match the pass (external_id, invoice id, currency, exact amount in centavos, `paid_amount` ≥ amount) before anything happens — a forged or premature "PAID" can't grant access. All decisions live in **`App\Service\PassService`** (shared with `reconcile_payments`). Xendit `PAID`/`SETTLED` → the pass becomes `paid` with `expires_at` = (existing active expiry for that reviewer, else now) + plan days, and the prior active pass becomes `superseded` — **one active pass per (user, reviewer)**; the claim (`WHERE status = 'pending'`) and the supersede commit in **one transaction**, so concurrent callbacks grant once. Xendit `EXPIRED` → `expired`. **Late payment:** a pass already `expired` (the EXPIRED notification won a race with a payment made at expiry) is still re-checked, and granted (`WHERE status = 'expired'`) if Xendit shows it paid — result `granted_late`, plus an error-level log line. Response codes tell Xendit whether to retry: **200** handled (`result`: `granted`, `granted_late`, `expired`, `expired_unpaid`, `already_handled`, `unknown_pass`, `mismatch` (logged), `invoice_not_found` (logged)); **503** when the callback says paid but Xendit's API doesn't show it yet (`still_pending`/`expired_unpaid`), or Xendit is unreachable; **500** when our side failed (nothing half-written). Xendit was observed (staging, Test Mode) to retry a failed delivery once ~15 min later, to whatever URL is configured *at retry time*.
- **`myPasses()`** (`GET /api/purchases`, logged-in) — the user's active passes, used by the `/checkout/success` poll.
- **`history()`** (`GET /api/billing/history`, logged-in) — every pass the user has paid for (`PassesTable::historyForUser()`). Backs the "Payment history" list in Settings and the printable receipt at `/billing/:reference` (`src/pages/Receipt.js`, full-bleed, `print:` variants; titled "Invoice" with the pass reference as the invoice number, and splits the VAT-inclusive plan price into VATable sales + 12% VAT, computed in centavos so the parts always sum to the total; a payment confirmation, explicitly **not** a BIR Official Receipt).

`session()` / `login()` / `googleLogin()` attach a **`purchases`** array to the returned user (`UsersController::withPurchases()` → `PassesTable::activeForUser()`), which is what `getPurchases(user)` in `reviewers.js` reads. Each entry carries `planId` (`7-day`/`30-day`/`90-day`) alongside the display `plan` name. `index.js` now rewrites `localStorage['skillsprint_user']` from every `/api/session` poll so passes stay current app-wide. Frontend: `startCheckout()` in `src/api.js`; `src/pages/Checkout.js` is the post-redirect success (polls, then opens the reviewer) / cancel pages, routed in `Dashboard.js`.

**bfcache gotcha on the Buy buttons.** `startCheckout()` redirects via `window.location.assign(invoice_url)`, which doesn't unmount `DashboardPlans.js`/`Pricing.js` — the browser just freezes the page mid-navigation. Hitting Back restores that exact frozen snapshot from the back/forward cache instead of re-running the page, so without a fix the clicked button stays stuck on "Redirecting…", disabled, forever (not a security issue — the pending pass/invoice already exists server-side either way, and the checkout dedup guard above covers a real re-click — just a dead-looking page). Both pages listen for `pageshow` and check `event.persisted` (specifically means "restored from bfcache") to reset the busy state when it fires. Any new page that redirects away mid-flow (another payment-adjacent one, say) needs the same guard.

**Plan-tier gating (mock exams).** Per `plans.js`'s `COMPARISON` matrix, mock exams is a 30-day/90-day-only feature — the 7-day plan excludes it. This is enforced only on the **frontend** today, in `src/pages/MockExams.js` (routed at `/mock-exams` in `Dashboard.js`): it reads `getPurchases(user)`'s `planId` for `civil-service` and shows one of three states — no pass → "get a pass"; a `7-day` pass → an upgrade prompt naming what they have and what unlocks it; `30-day`/`90-day` → "coming soon" (the mock-exam feature itself isn't built yet, so even an entitled holder can't do anything yet — the gate is real, the destination isn't). The "Mock exams" card in `Review.js` is deliberately always shown/clickable regardless of plan — the tier check happens on click-through, not by hiding the entry point. **There is no backend enforcement of this tier split** — `Api\AppController`'s gate (private `hasActivePass(int $userId)`, and anything modelled on it) only checks "any active paid pass," with no `plan_id` awareness; a future server-side mock-exam endpoint must not reuse it as-is, or a 7-day holder could bypass the frontend gate directly against the API.

**`reconcile_payments`** (`src/Command/ReconcilePaymentsCommand.php`) repairs what the webhook missed, with the same `PassService` rules: every `pending` pass between `--min-age` minutes and `--max-age` hours old is checked against Xendit (paid → granted, expired → expired, mismatch → reported), a pending pass Xendit has **no** invoice for is marked `failed` after `--fail-after` hours (checkout died before the invoice existed), and `expired` passes created within `--expired-max-age` hours are re-checked for a late payment (`granted_late`; unpaid ones are only counted as `expired_unpaid` — abandoned checkouts aren't noise). Every write is conditional on the status it read, so it's safe to run repeatedly or alongside the webhook; it exits non-zero on a mismatch, an error, or Xendit being unreachable so a scheduler can alert. **Nothing schedules it yet** — a Railway cron (e.g. every 10 min) is needed before launch.

Xendit account is in **Test Mode** until the business is verified — the whole flow works with test payment methods; going live is just swapping `XENDIT_SECRET_KEY`.

**SPA route split.** `src/index.js` → `AppWrapper` picks the whole route tree by auth state: logged-out renders `src/App.js` (guest routes only: `/`, `/login`, `/explore`, `/pricing`, everything else `<Navigate to="/">`), logged-in renders `src/pages/Dashboard.js` (which owns the authenticated route tree). `/account-setup` is wired above the split so it renders in both states. So a new guest page goes in `App.js`, a new authenticated page in `Dashboard.js`. `src/pages/*` are the authenticated screens (Settings, Profile, Review, MyLibrary, …); `src/components/*` the shared/landing pieces. `src/old_file/` (`index_old.js`, `App_old.js`) is dead pre-rewrite code — don't edit it.

### Data Model

All tables use non-standard primary keys (not `id`):

- **`users`** — PK: `user_id` (**`INT UNSIGNED`**). Fields: `fname`/`lname` (`VARCHAR(50) NOT NULL`), `email` (`VARCHAR(100) NOT NULL`, DB-level unique — `users_email`; stored as the user typed it, but **every comparison ignores letter case** — go through `UsersTable::normalizeEmail()` / `findByEmailAddress()` / `emailTaken()` (an explicit `LOWER(email) = …`) and the case-insensitive `uniqueEmail` rule, and **never look an account up with `where(['email' => …])` directly**: production's collation `utf8mb4_0900_ai_ci` ignores case but the SQLite test DB doesn't. That collation also treats accented and unaccented letters as equal, which the app doesn't fold; such a clash hits the unique index and reads as "already registered" — accepted, H3), `user_name` (`VARCHAR(50) NOT NULL`, DB-level unique — `users_user_name`), `user_pass` (`password_hash` digest, `VARCHAR(255)` nullable — null for Google-only accounts), `google_id` (`VARCHAR(255)` nullable, DB-level unique — `users_google_id` on Railway, `uniq_google_id` locally, same constraint; set by `googleLogin()`), `session_token` (`VARCHAR(64)` nullable — the single-device session guard, see Authentication), `email_verified_at` (`DATETIME` nullable, after `session_token` — NULL = email not verified, and such an account never gets a session; see Authentication → Email verification; every account that existed when it was added was backfilled as verified). This is the schema **confirmed directly against Railway production** on 2026-09-10 — a prior version of this doc (and of local's actual table) had it wrong: signed `user_id`, nullable/narrower `fname`/`lname`/`email`/`user_name` with no DB-level uniqueness on the latter two, narrower `google_id`. Local was fixed to match production, not the other way around — see the FK signedness note below. **`users` predates migrations** and already exists for real on every DB (local + Railway) — its migration, `20260528000000_CreateUsers.php`, exists **only** so the SQLite test schema (built from scratch, purely from migrations) has something for `users`-FK migrations (`auth_codes`, `passes`, `topic_reviews`) to reference; it must never actually run against a real database (see the Migrations paragraph below for how to handle a new DB).
- **`topics`** — PK: `topic_id`. Fields: `name` (max 100), `description`. `hasMany` Questions, `hasOne` TopicReviews (exposed on the entity as `$topic->topic_review`, singular — see note below on the association alias).
- **`questions`** — PK: `question_id`. Fields: `topic_id` (FK → topics, CASCADE delete), `question_text`, `difficulty` (1=easy/2=medium/3=hard, constants on `QuestionsTable`), `explanation` (`$_hidden` — never in JSON; only `answer()` returns it). `belongsTo` Topics, `hasMany` Choices (sorted by `sort_order ASC`).
- **`choices`** — PK: `choice_id`. Fields: `question_id` (FK → questions, CASCADE delete), `choice_text`, `is_correct` (boolean, `$_hidden` — never in JSON, so a new endpoint that must expose it has to do so deliberately), `sort_order`. `belongsTo` Questions.

Content is loaded with **`bin/cake import_questions <file.csv>`** (`src/Command/ImportQuestionsCommand.php`): one row per question — `topic, question, difficulty (easy/medium/hard), explanation, choice_a…choice_e, answer (letter)`. Topics are created on demand; a row whose `(topic, question)` already exists is skipped, so re-running a file is safe. Validation is all-or-nothing. Template + examples: `resources/careerpass_question_bank_1000_v2.csv`.

- **`auth_codes`** — PK: `auth_code_id`. Fields: `user_id` (FK → users, CASCADE), `purpose` (`'password_reset'`, `'set_password'`, `'login_challenge'`, `'verify_email'`, `'link_google'`, `'change_email'`, `'email_change_reauth'` (H3; both bound to the new address), plus code-less `'verify_email_sent'` / `'link_google_sent'` / `'change_email_sent'` / `'email_change_reauth_sent'` rows — one per code email sent, empty `code_hash`, backing each purpose's resend cooldown/daily cap; they currently stay after the account is verified or linked, ACTION_PLAN L14), `code_hash` (bcrypt of the 6-digit code, `$_hidden`), `expires`, `attempts`. One-time emailed codes; a row is deleted on use, expiry or after 5 bad guesses. `AuthCodesTable` / `AuthCode` entity.
- **`login_events`** — PK: `login_event_id`. Fields: `user_id` (FK → users, CASCADE), `device_hash`, `created`. Backs the rapid device-switch guard (see Authentication → "Rapid device-switch guard"); a user's rows are deleted when a correct challenge code clears the guard. `LoginEventsTable` / `LoginEvent` entity.
- **`login_attempts`** — PK: `login_attempt_id`. Fields: `identifier` (lowercased submitted username/email — **no users FK**, a guess can name a non-existent account), `created`. Backs the password brute-force throttle in `login()`; rows are cleared on a correct password for that identifier and pruned after a day. `LoginAttemptsTable` / `LoginAttempt` entity.
- **`passes`** — PK: `pass_id`. Fields: `user_id` (FK → users, CASCADE), `reviewer` (`civil-service`), `plan_id` (`7-day`/`30-day`/`90-day`), `amount`, `currency`, `external_id` (unique — our Xendit ref), `xendit_invoice_id`, `invoice_url` (the hosted-checkout URL — persisted so `checkout()` can hand back the same link on a near-immediate repeat call instead of minting a new invoice; see Payments), `status` (`pending`→`paid`/`expired`; `pending`→`failed` only via `reconcile_payments` when Xendit has no invoice; `expired`→`paid` for a late payment; `paid`→`superseded` when a later pass extends it), `paid_at`, `expires_at`, `created`/`modified`. Backs Payments (see the Payments section). `PassesTable` (`activeForUser()`, `activeForReviewer()`) / `Pass` entity.
- **`topic_reviews`** — PK: `topic_review_id`. Fields: `topic_id` (FK → topics, CASCADE, **unique** — one review per topic in v1), `author_id` (nullable FK → users, `SET NULL`; unpopulated in v1 — all content is site-authored; exists now so attributing a write-up to an individual professional later doesn't need another migration — see the "Topics as Review Content" product note), `content` (the study/explainer text). Loaded with `bin/cake import_topic_reviews <file.csv>` (columns: `topic`, `content`; the topic must already exist — this command never creates one). Unlike `import_questions`, re-running the same file *updates* the row instead of skipping it. `TopicReviewsTable` / `TopicReview` entity; the association alias on `Topics` is **`TopicReviews`** (plural, matching this table's class), not `TopicReview` — CakePHP resolves the table name from the alias when no `className` is given, so a singular alias here would (and initially did) look for a nonexistent `topic_review` table.

Migrations: `users` in `20260528000000_CreateUsers.php` (test-schema-only — see the `users` bullet above, **never** run for real); topics/questions/choices in `20260529000000_CreateTopicsQuestionsChoices.php`; `auth_codes` + `login_events` in `20260907000000_CreateAuthCodes.php`; `login_attempts` in `20260908000000_CreateLoginAttempts.php`; `passes` in `20260909000000_CreatePasses.php`; `topic_reviews` in `20260910000000_CreateTopicReviews.php`; `passes.invoice_url` in `20260911000000_AddInvoiceUrlToPasses.php`; `users.email_verified_at` (+ backfill of existing accounts as verified) in `20261016000000_AddEmailVerifiedAtToUsers.php`. **`docker-start.sh` does not run migrations.** All eight are applied on Railway staging and production (the eighth hand-applied on 2026-10-16/17 with a guarded script *before* the B3-V code deployed, and recorded with `mark_migrated` only once that code — which contains the migration file — was running). **Local dev:** after pulling B3-V, run `bin\cake migrations migrate` once — it applies only the eighth, since the first seven are recorded — or every local account reads as unverified and can't sign in. **Before ever running `bin/cake migrations migrate` against a *new* real database for the first time** (a new environment, a rebuilt Railway MySQL service), run `bin/cake migrations mark_migrated --target 20260528000000 --only` first, or `migrate` will try to `CREATE TABLE users` against a database where it already exists and fail. If new tables/columns are ever hand-applied again instead of migrated (keeping with this app's established pattern), match production's real types — `INT UNSIGNED` for every FK to `users.user_id` (it's unsigned), e.g.:
```sql
CREATE TABLE topic_reviews (topic_review_id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY, topic_id INT UNSIGNED NOT NULL, author_id INT UNSIGNED NULL, content TEXT NOT NULL, created DATETIME NULL, modified DATETIME NULL, UNIQUE KEY (topic_id), FOREIGN KEY (topic_id) REFERENCES topics(topic_id) ON DELETE CASCADE, FOREIGN KEY (author_id) REFERENCES users(user_id) ON DELETE SET NULL);
ALTER TABLE passes ADD COLUMN invoice_url VARCHAR(255) NULL AFTER xendit_invoice_id;
ALTER TABLE users ADD COLUMN email_verified_at DATETIME NULL DEFAULT NULL AFTER session_token;
UPDATE users SET email_verified_at = NOW() WHERE email_verified_at IS NULL;   -- B3-V backfill, once
```

**FK signedness.** Every FK column pointing at `users.user_id` (including `topic_reviews.author_id`) must be `INT UNSIGNED` — production's `users.user_id` is unsigned. A past `errno 150` locally came from *local's* `users` table having drifted to signed, not from the migrations; making the FKs signed would have broken production. When a migration's FK to a legacy, unmigrated table fails, check that table's real definition in every environment before deciding which side is wrong.

**`composer test` baseline:** passes from scratch (189 tests) with `OK, but there were issues!` — the "issues" are PHPUnit deprecation notices, not failures or incomplete stubs. `ApplicationTest::testMiddleware` and `PagesControllerTest`'s CSRF tests were deliberately changed from the skeleton's versions to match this app's middleware (see "CORS & Middleware").

Other info-level logging stays file-only.

No redirect URIs are needed (the Google button returns the ID token in the browser). A new frontend domain that isn't added here gets a silent `403` / "origin not allowed" on the Google button.

All other errors fall through to `WebExceptionRenderer`.

### Testing

Tests live in `tests/TestCase/`, mirroring `src/`. Integration tests use `IntegrationTestTrait`. The test **schema** comes entirely from migrations — `tests/bootstrap.php` runs `(new Migrator())->run()` against SQLite before any test runs (`tests/schema.sql` is an empty placeholder, unused); this is why `users` needed its own migration (test-schema-only, see Data Model → `users`) even though it's otherwise unmigrated. Fixtures in `tests/Fixture/` (e.g. `UsersFixture`) supply **rows**, not schema — they introspect the already-migrated table for column types. There is a fixture for every table.

Two shared traits in `tests/TestSuite/` are the way to write API integration tests — reuse them, don't hand-roll the auth setup:
- **`ApiTestTrait`** — `asAjax()` sends the `X-Requested-With` header (without it every auth action 403s, see CORS & Middleware). `loginAs($userId)` rotates `users.session_token` and writes the matching `Auth.User`/`Auth.token`, exactly as `startSession()` does (a session without the token match reads as "signed in elsewhere"). `responseJson()` decodes the body, and `setEnv()`/`restoreEnv()` let a test override `env()` values.
- **`XenditTestTrait`** — a fake Xendit built on `HttpClientTrait` mock responses (`App\Payment\Xendit` goes through `Cake\Http\Client`). `fakeXenditEnv()` in `setUp()` sets fake credentials and registers a guard mock, which puts Cake's `Client` in mock-only mode: any request without a matching mock fails (surfacing as `XenditException`) instead of reaching the network — so a test that *doesn't* fake a response also proves no Xendit call was made. `xenditInvoiceFor($pass, $status, $overrides)` builds Xendit's invoice record for a pass (override fields to simulate mismatches); `fakeXenditGetInvoice()`/`fakeXenditGetInvoiceError()`/`fakeXenditFindByExternalId()` answer the lookups; `fakeXenditCreateInvoice()`/`fakeXenditCreateInvoiceFailure()` stub checkout; `postXenditWebhook()` sends a callback with the token. Requires `ApiTestTrait`.

Google sign-in is tested two ways. Most tests replace the verifier with `$this->mockService(GoogleTokenVerifierInterface::class, …)` returning chosen claims (see `UsersVerificationTest::fakeGoogle()`). To exercise the **real** `GoogleTokenVerifier` without the network, **`GoogleKeysTestTrait`** gives it an HTTP client that serves a fixed Google-style key set (`googleKeysHttp()`) and builds well-formed, unsigned ID tokens (`fakeIdToken($kid)`). Its handler never runs dry on purpose: a queue-based Guzzle `MockHandler` throws `OutOfBoundsException` when empty — the same exception php-jwt throws for an unknown key id — which would make such a test pass for the wrong reason. Linking Google to an existing account (B3-L) is covered by `tests/TestCase/Controller/UsersGoogleLinkTest.php` (code step, right/wrong/expired codes, cooldown and cap, separate limits per purpose, the 409 for a different linked Google account, codes tied to their account).

Email changes (H3) and case-insensitive email handling across sign-in, Google sign-in, password reset and registration are covered by `tests/TestCase/Controller/UsersEmailChangeTest.php` (both re-authentication paths, address-bound codes, limits, gates, the `updateAccount` 422, and a mixed-case end-to-end). The content gate (H1) is covered by `tests/TestCase/Controller/Api/ContentAccessTest.php` (no session, replaced session, pre-token session, no/expired/superseded pass, active pass, writes, unverified and deleted accounts). The question-bank lockdown (H2) is covered by `QuestionsLockdownTest.php` (no list/view, no answer key in practice, the answer endpoint's 200/403/404/422/405 cases, the 200-question served cap). Its 404 test turns `debug` off: the debug error page quotes source lines from the stack, including the test's own needle, which made it fail on PHP 8.3. Because `IntegrationTestTrait` doesn't carry the session between requests, those tests read the served list straight from `$_SESSION` (reading it through `$this->_requestSession` after a completed request restarts the CLI session and empties it).

**Local test database after a new migration.** The local SQLite test DB (`tmp/tests.sqlite`) persists between runs, and the Migrator only applies the migrations it's missing. With `cacheMetadata` on, CakePHP caches table schemas (2 minutes in debug mode), and the first run after a new migration can cache the table's *old* schema: fixtures then insert rows without the new column. After B3-V this made every signed-in test fail as `signed_out` (fixture users lost `email_verified_at`, so they read as unverified) until the cache expired. If a checkout's first run after pulling a migration fails like that, clear the cache (`rm tmp/cache/models/myapp_cake_model_test_*`, or `bin/cake schema_cache clear --connection test`) and rerun. CI is unaffected: it builds a fresh database every run. Frontend: the only maintained Jest test is `webroot/react-frontend/src/sessionErrors.test.js` (which 401s count as a dead session). Run it with `npx react-scripts test --watchAll=false --testPathPattern sessionErrors` from `webroot/react-frontend/`. It imports `sessionErrors.js` only — importing `api.js` would pull in axios's ES-module build, which CRA's Jest can't load without extra config. `src/App.test.js` is the stale CRA placeholder (it fails), and frontend tests don't run in CI.

### Static Analysis & Code Style

- PHPStan at level 8, analyzing `src/` only (`phpstan.neon`). Pre-existing findings are frozen in **`phpstan-baseline.neon`**. New code must pass clean; don't regenerate the baseline to hide new errors. Shrink it as baselined code gets touched. A finding that is provably wrong gets a one-line `@phpstan-ignore <identifier>` with a comment saying why — e.g. `GoogleTokenVerifier` catches `OutOfBoundsException`, which PHPStan calls a dead catch because google/apiclient doesn't declare that php-jwt throws it (`GoogleTokenVerifierTest` proves it does).
- PHPCS uses the `CakePHP` ruleset, applied to `src/` and `tests/` (`phpcs.xml`); return type hints are excluded from controller files. The codebase has a **backlog of existing violations**, so a full `composer cs-check` (and therefore `composer check`) reports failures you didn't cause. CI checks only the PHP files a push/PR changes, so any file you touch must come out clean. Check it with `vendor/bin/phpcs <files>`.

### CI & Branches

`.github/workflows/ci.yml` runs on pushes to `master`, `staging` and `fix/**`, and on PRs into `master`. It runs PHPUnit on PHP 8.2 (prod's version) and 8.3 against SQLite (`DATABASE_TEST_URL`). It also runs `composer audit --no-dev` (fails on any advisory in a production dependency), PHPCS on changed files, and PHPStan. Work happens on `fix/<id>-<slug>` branches (IDs like B8/B10 come from the audit remediation plan), validated on staging (merged into `staging`, which deploys the staging environment — see **Deployment → Staging**), then merged into `master` with a `Merge Bx: …` commit. A push to `master` deploys production. The git remote is named **`review-app`**, not `origin`. To work on a branch without touching an uncommitted main checkout, use a `git worktree` at a **short** path (e.g. `C:\xampp\htdocs\<name>`; long paths break `vendor/` on Windows) with a **real copy** of `vendor/` plus `composer dump-autoload` — a junction/symlinked `vendor/` makes Composer autoload `App\` from the main checkout, so tests silently run the wrong code.

### Deployment

The `Dockerfile` builds a `php:8.2-apache` image with `pdo_mysql`, sets `DocumentRoot` to `webroot/`, and installs Composer deps without dev packages. `docker-start.sh` is the entrypoint (fixes the Apache MPM conflict → prefork, enables `mod_rewrite`). Railway hosts the backend + a MySQL service; Cloudflare Pages hosts the frontend.

**Railway.** Project `glorious-amazement`, two environments, each with its own `reviewer-app` + `MySQL` service instances. **Production is always-on**: `railway.toml` on `master` sets `deploy.sleepApplication = false` (the deploy manifest is what applies — the dashboard's service-level toggle has been seen to read `true` while the deployed manifest said `false`), and production MySQL sleep is off. **Staging is allowed to sleep**, via a staging-only `[environments.staging.deploy] sleepApplication = true` block that lives on the `staging` branch (verified honored: staging's manifest says `true`, production's `false`). Production deploys on every push to `master`, staging on every push to `staging`; both wait for CI to pass. `docker-start.sh` does **not** run migrations — apply new tables/columns by hand (see **Data Model**). Railway stops reading `railway.toml` on 2026-12-01 — the move to `.railway/railway.ts` (ACTION_PLAN M11) must carry both sleep settings.

**Staging.** Railway environment `staging`: deploys the `staging` branch. **Frontend `https://staging.career-pass.org`** — Cloudflare Pages' branch alias for `staging` (`staging.reviewer-app.pages.dev`; the `staging` DNS CNAME points at that alias, not at `reviewer-app.pages.dev`, which would serve production), built with the Pages **Preview** env vars `REACT_APP_API_URL=https://api-staging.career-pass.org` and the same `REACT_APP_GOOGLE_CLIENT_ID` as production (Preview vars apply to every non-production branch, so `fix/*` previews also call staging — and can't sign in, since staging's CORS allows only `staging.career-pass.org`). **API `https://api-staging.career-pass.org`** — a Railway custom domain on staging's `reviewer-app` (port 80, like production's `api`); `https://reviewer-app-staging.up.railway.app` still works and is where the Xendit Test Mode callback points. Frontend and API are same-site, like production. Its own MySQL 9.7.2 (`DATABASE_URL = ${{MySQL.MYSQL_URL}}`, which resolves to the staging instance on staging's private network), built from production's schema export with migration history recorded via `mark_migrated` and content imported from the repo CSVs — no production data. `FRONTEND_URL=https://staging.career-pass.org`; Xendit/Brevo test credentials; staging test accounts only. Because it sleeps, the first request after idle is a cold start, and **SSH into a sleeping instance lands on Railway's account-info service instead of the container — wake it with a `curl` first**. Running commands inside it: register a temporary key (`railway ssh keys add` only finds keys in `~/.ssh`), take the target from `railway ssh config --dry-run -p <project> -e <env> -s <service>`, connect with plain `ssh -i <key> <user>@ssh.railway.com "…"` (the CLI's own `railway ssh` failed host-key verification), use `php bin/cake.php`, and remove the key afterwards — while registered it also grants account-level Railway SSH tools. Sessions live on the container's disk, so every deploy (or cold start) signs everyone out (ACTION_PLAN B4).
